# Data Model — FROZEN in Phase 2

> **This file is the contract.** The simulator, the API, the database and the dashboard are all written against this document and nothing else. Risk N1 (components that don't fit together) is prevented here or not at all. Any change must be made *here first*, then in the code, and announced to the team.

## 1. The event — canonical JSON

Taken from the spec's Appendix A and extended only where we need it. Fields marked **added** are ours.

```json
{
  "event_id":   "evt-2026-0001",
  "building":   "Library-A",
  "room":       "A203",
  "event_type": "occupancy",
  "value":      42,
  "unit":       "people",
  "severity":   "normal",
  "timestamp":  "2026-05-10T09:30:00Z"
}
```

| Field | Type | Required | Rule | Notes |
|---|---|---|---|---|
| `event_id` | string | yes | `evt-<YYYY>-<NNNN>` or a UUID; max 64 chars | Generated by the simulator; the API rejects duplicates by overwriting deterministically |
| `building` | string | yes | one of the known buildings, max 40 chars | `Library-A`, `Science-B`, `Arts-C`, `Sports-D`, `Admin-E` |
| `room` | string | yes | max 20 chars | `A203`. Use `-` for building-level readings such as an energy meter |
| `event_type` | string | yes | enum, see §2 | Drives which rule runs |
| `value` | number | yes | finite, within the per-type range | Rejected if not a number |
| `unit` | string | yes | must match the type's expected unit | Guards against a sensor sending °F where we expect °C |
| `severity` | string | **server-controlled** | `normal` \| `warning` \| `critical` | **The client's value is ignored and recomputed.** A sensor must not be able to declare itself normal |
| `timestamp` | string | yes | ISO-8601 UTC, ending in `Z`; not more than 24 h in the past or 5 min in the future | Everything in this system is UTC |
| `source` **added** | string | no | `simulator` \| `staff-portal` | How it arrived |
| `received_at` **added** | string | server | ISO-8601 UTC | Set by `cp-ingest`, lets us measure ingestion lag |
| `expires_at` **added** | number | server | Unix epoch seconds, `received_at` + 30 days | DynamoDB TTL — see §5 |
| `message` **added** | string | no | max 280 chars | Only for `service_request`: what the student is asking for |

## 2. Event types, units and rules

| `event_type` | `unit` | Normal range | → `warning` | → `critical` |
|---|---|---|---|---|
| `occupancy` | `people` | 0 … room capacity | > 100 % of capacity | > 120 % of capacity |
| `temperature` | `celsius` | 18 … 26 | outside 18-26 | outside 15-30 |
| `humidity` | `percent` | 30 … 60 | outside 30-60 | outside 20-70 |
| `energy` | `kwh` | 0 … building baseline | > 1.5 × baseline | > 2 × baseline |
| `equipment` | `status` | `value` = 0 (OK) | `value` = 1 (degraded) | `value` = 2 (failed) |
| `service_request` | `priority` | `value` = 1 (low) | `value` = 2 (normal) | `value` = 3 (urgent) |

Room capacities and building baselines live in one shared config file (`backend/src/common/campus_config.py`), imported by both the simulator and `cp-ingest`, so the two can never disagree about what "overloaded" means.

**An event is an alert when `severity != "normal"`.** That is the only definition used anywhere in the system.

## 3. DynamoDB table

**Table:** `campuspulse-events` · **capacity:** on-demand · **encryption:** at rest with the AWS-owned key (default) · **PITR:** enabled.

| Attribute | Role | Value |
|---|---|---|
| `pk` | Partition key | `DAY#<YYYY-MM-DD>` — the UTC date from `timestamp` |
| `sk` | Sort key | `<timestamp>#<event_id>` |
| `gsi1pk` | GSI1 partition key | `BLD#<building>#<YYYY-MM-DD>` |
| `gsi1sk` | GSI1 sort key | same as `sk` |
| `gsi2pk` | GSI2 partition key | `ALERT#<YYYY-MM-DD>` — **written only when `severity != normal`** |
| `gsi2sk` | GSI2 sort key | same as `sk` |
| `gsi3pk` | GSI3 partition key *(Oct 2026)* | `USER#<cognito sub>` — **written only for service requests** |
| `gsi3sk` | GSI3 sort key | same as `sk` |
| `requested_by` | attribute | the requester's email — returned to administrators only |
| `expires_at` | TTL attribute | epoch seconds |
| …plus every field from §1 | | |

### Why this key design

Sort keys in DynamoDB are stored in order, so a key of `<timestamp>#<event_id>` means "newest events" is a query with `ScanIndexForward=false` and a `Limit` — not a scan of the table. Putting the **date** in the partition key keeps each day's events together so "today's activity" is one partition read.

**GSI2 is a sparse index** and it is the neatest thing in this design: an item only appears in a GSI if it has that index's key attributes. `cp-ingest` writes `gsi2pk` **only for non-normal events**, so the alerts index physically contains alerts and nothing else. `GET /alerts` reads a small index instead of filtering a big table — cheaper, faster, and a genuinely good answer when the professor asks how you'd avoid scanning.

### Access patterns — every query this system will ever run

| # | Need | Index | Key condition |
|---|---|---|---|
| 1 | 50 most recent events across campus | table | `pk = DAY#<today>`, reverse, limit 50 |
| 2 | Recent events for one building | GSI1 | `gsi1pk = BLD#<building>#<today>`, reverse |
| 3 | Active alerts | GSI2 | `gsi2pk = ALERT#<today>`, reverse |
| 4 | Everything today, for statistics | table | `pk = DAY#<today>` |
| 5 | One specific event | table | `pk` + `sk` |
| 6 | A student's own service requests *(Oct 2026)* | GSI3 (sparse) | `gsi3pk = USER#<sub from the verified token>`, reverse |
| 7 | All service requests of a day, admin view *(Oct 2026)* | table | `pk = DAY#<date>`, filter `event_type = service_request`, paged |

**There is no `Scan` anywhere in this design.** If a feature ever seems to need one, the key design is wrong — raise it rather than adding a scan.

### The known weakness, stated before we are asked

All of one day's writes land in one partition. A DynamoDB partition sustains roughly 1,000 write units per second, so this design tops out around a thousand events per second — far beyond our prototype, but it is a real ceiling.

**The fix, if volume demanded it:** add a shard suffix, `DAY#2026-09-22#<0-9>`, spreading writes over ten partitions and reading all ten in parallel. We are not implementing this; we are describing it in the scalability section because knowing your design's limit and its remedy is worth more marks than pretending it has none.

## 4. Users

Users live in **Cognito**, not DynamoDB. No users table.

| Group | Members | May call |
|---|---|---|
| `admin` | Campus administrators (and the simulator's account) | everything: `POST /events`, `GET /events`, `/alerts`, `/stats`, all requests |
| `student` | Students | `/stats`, `POST /requests`, `GET /requests` (**own only**) — **not** `/events`, **not** `/alerts` |

*Renamed from `ops`/`staff` after the project review (October 2026), which asked for one administrator page and one student page.* Demo users: `admin@northbridge.edu` (admin), `student@northbridge.edu` (student), and `device@campuspulse.local` in `admin` for the simulator.

## 5. Retention — TTL

Every item carries `expires_at` = 30 days after ingestion. DynamoDB deletes expired items automatically, at no charge for the deletion.

Three reasons: storage stays far inside the 25 GB free allowance; a smaller table restores faster, which improves our RTO; and it is a real data-lifecycle decision to discuss in the report. For a real campus we would export to S3 before expiry for long-term analytics — described in "Future improvements", not built.

## 6. Worked example

The simulator produces:

```json
{ "event_id": "evt-2026-0042", "building": "Library-A", "room": "A203",
  "event_type": "occupancy", "value": 58, "unit": "people",
  "severity": "normal", "timestamp": "2026-09-22T14:05:00Z" }
```

Room `A203` has capacity 45. `58 / 45 = 129 %` → above 120 % → **critical**. The client said `normal`; the server overrules it. The stored item:

```json
{ "pk": "DAY#2026-09-22",
  "sk": "2026-09-22T14:05:00Z#evt-2026-0042",
  "gsi1pk": "BLD#Library-A#2026-09-22",
  "gsi1sk": "2026-09-22T14:05:00Z#evt-2026-0042",
  "gsi2pk": "ALERT#2026-09-22",
  "gsi2sk": "2026-09-22T14:05:00Z#evt-2026-0042",
  "event_id": "evt-2026-0042", "building": "Library-A", "room": "A203",
  "event_type": "occupancy", "value": 58, "unit": "people",
  "severity": "critical", "timestamp": "2026-09-22T14:05:00Z",
  "source": "simulator", "received_at": "2026-09-22T14:05:01Z",
  "expires_at": 1761746701 }
```

It is now returned by access patterns 1, 2, 3 and 4 — recent events, that building, the alerts list, and today's statistics — from a single write.
