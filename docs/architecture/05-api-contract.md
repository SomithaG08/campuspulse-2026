# API Contract — CampusPulse 2026

Base URL (after deployment): `https://<api-id>.execute-api.eu-west-3.amazonaws.com` — **not deployed yet**.

Every endpoint the spec's Appendix B requires is here. The two extras are marked.

## Conventions

- **Everything is JSON**, request and response, `Content-Type: application/json`.
- **Everything is HTTPS.** There is no HTTP listener to downgrade to.
- **Authentication** is a Cognito ID token sent as `Authorization: Bearer <token>`, except on `POST /login`.
- **Times are UTC ISO-8601**, always ending in `Z`.
- **Errors always look the same:**
  ```json
  { "error": "ValidationError", "message": "value must be a number", "request_id": "abc-123" }
  ```
  `request_id` is the Lambda request ID — it is also in the CloudWatch log, which is how support questions get answered in seconds instead of minutes.

## Status codes used

| Code | Meaning here |
|---|---|
| 200 | Fine |
| 201 | Event created |
| 400 | The request was malformed or failed validation — *your* fault, don't retry unchanged |
| 401 | No token, expired token, or bad signature — log in again |
| 403 | Valid token, wrong role — logging in again will not help |
| 429 | Throttled |
| 500 | Our bug |

## `POST /login`

Authenticates a user. **No token required.**

**Request**
```json
{ "username": "ops@northbridge.edu", "password": "••••••••" }
```

**200**
```json
{ "id_token": "eyJraWQi...", "expires_in": 3600, "role": "ops", "username": "ops@northbridge.edu" }
```

| Error | When |
|---|---|
| 400 | Missing username or password |
| 401 | Wrong credentials, or the user must change their password on first login |

**How it works:** `cp-auth` calls Cognito `InitiateAuth`. Our code never sees a stored password and never writes one anywhere. Failed attempts are logged **with the username but never the password**.

## `POST /events`

Submits one campus event. **Requires `ops`.** (The simulator's device user is in `ops`.)

**Request:** the event object from `04-data-model.md` §1. `severity` may be sent but is ignored.

**201**
```json
{ "event_id": "evt-2026-0042", "severity": "critical", "alert": true, "stored_at": "2026-09-22T14:05:01Z" }
```

The response tells the caller what the server decided — the simulator prints this, which is what makes the live demo legible.

| Error | When |
|---|---|
| 400 | Missing field, unknown `event_type`, wrong `unit`, non-numeric `value`, out-of-window `timestamp`, body larger than 4 KB |
| 401 | No/expired token |
| 403 | Token belongs to `staff` |
| 429 | Above the stage throttle |

## `GET /events`

Recent events, newest first. **Requires `ops` or `staff`.**

| Query param | Default | Max | Meaning |
|---|---|---|---|
| `limit` | 50 | 200 | How many |
| `building` | — | — | Filter to one building (uses GSI1) |
| `date` | today (UTC) | — | `YYYY-MM-DD` |

**200**
```json
{ "count": 2, "events": [ { "event_id": "...", "building": "Library-A", "room": "A203",
    "event_type": "occupancy", "value": 58, "unit": "people", "severity": "critical",
    "timestamp": "2026-09-22T14:05:00Z" } ], "next_token": null }
```

`next_token` carries DynamoDB's pagination cursor. 400 if `limit` is not 1-200.

---

## `GET /alerts`

Only events with `severity != normal`, newest first. **Requires `ops`.** Reads the sparse GSI2, so it never touches normal events.

| Query param | Default | Meaning |
|---|---|---|
| `limit` | 50 | Max 200 |
| `severity` | both | `warning` or `critical` |
| `date` | today | `YYYY-MM-DD` |

**200**
```json
{ "count": 1, "critical_count": 1, "warning_count": 0,
  "alerts": [ { "event_id": "evt-2026-0042", "building": "Library-A", "room": "A203",
    "event_type": "occupancy", "value": 58, "severity": "critical",
    "reason": "occupancy 58 exceeds 120% of capacity 45",
    "timestamp": "2026-09-22T14:05:00Z" } ] }
```

`reason` is generated by the rule that fired. It turns a number into something an operator can act on, and it is what you point at during the demo.

## `GET /stats`

Aggregated campus state. **Requires `ops` or `staff`.**

| Query param | Default | Meaning |
|---|---|---|
| `date` | today | `YYYY-MM-DD` |
| `building` | all | Restrict to one building |

**200**
```json
{
  "generated_at": "2026-09-22T14:10:00Z",
  "date": "2026-09-22",
  "total_events": 512,
  "alert_count": 17,
  "events_by_type":     { "occupancy": 210, "temperature": 150, "humidity": 80, "energy": 52, "equipment": 12, "service_request": 8 },
  "events_by_severity": { "normal": 495, "warning": 12, "critical": 5 },
  "current_occupancy":  [ { "building": "Library-A", "room": "A203", "value": 58, "capacity": 45, "load_pct": 129 } ],
  "avg_temperature_c":  { "Library-A": 22.4, "Science-B": 24.1 },
  "energy_kwh_by_building": { "Library-A": 310.5, "Science-B": 512.0 },
  "top_energy_building": "Science-B",
  "urgent_requests": 2
}
```

Every one of the operational questions in the spec (§2) is answerable from this single response — which is the point, and worth saying out loud at the oral.

## `POST /requests` *(extra, not in Appendix B)*

A student service request. **Requires `staff` or `ops`.** Exists so the `staff` role can *do* something rather than only read — the spec asks for two roles with different permissions, and a role that can only read is a thin demonstration.

**Request**
```json
{ "building": "Library-A", "room": "A203", "message": "Projector not working", "priority": 3 }
```

Stored as an event with `event_type: "service_request"`, `value: priority`, `unit: "priority"`, `source: "staff-portal"`. Priority 3 becomes `critical` and therefore appears in `/alerts` — so a student request and a broken sensor flow through exactly the same pipeline. One path, two stories.

**201** `{ "event_id": "evt-...", "severity": "critical", "alert": true }`

---

## `GET /health` *(extra)*

No authentication. Returns `{ "status": "ok", "version": "..." }`. Used by the demo-day smoke test to warm the function and prove the API is reachable before anything else is tried.

## Permission matrix

| Endpoint | none | `staff` | `ops` |
|---|---|---|---|
| `POST /login` | ✅ | ✅ | ✅ |
| `GET /health` | ✅ | ✅ | ✅ |
| `POST /events` | 401 | **403** | ✅ |
| `GET /events` | 401 | ✅ | ✅ |
| `GET /stats` | 401 | ✅ | ✅ |
| `GET /alerts` | 401 | **403** | ✅ |
| `POST /requests` | 401 | ✅ | ✅ |

The two **403** cells are the authorization demo. Have that curl command ready in the demo script.

## Where each check happens

1. **API Gateway JWT authorizer** — is the token real, unexpired, and issued by our pool? If not, 401, and our code never runs.
2. **Lambda** — does `cognito:groups` contain a group allowed on this route? If not, 403.
3. **IAM** — may this function touch this table at all? Enforced by AWS regardless of what our code tries.

Three layers, each independently sufficient to stop a whole class of attack. Every team member should be able to recite them.
